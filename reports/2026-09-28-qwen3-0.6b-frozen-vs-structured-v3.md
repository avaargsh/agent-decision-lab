## Raw comparison

| Metric | Frozen candidate logits | Autoregressive structured output |
| --- | ---: | ---: |
| Accuracy | 0.5000 | 0.5000 |
| Brier | 0.1852 | 0.1900 |
| ECE | 0.4285 | 0.1500 |
| Mean latency | 14285.19 ms | 10368.51 ms |
| p50 latency | 14117.44 ms | 10324.06 ms |
| p95 latency | 15004.38 ms | 10546.19 ms |
| Mean tokens processed / decision | 125.5 | 101.5 |
| Coverage @ 0.5 | 0.50 | 1.00 |
| Selective risk @ 0.5 | 0.00 | 0.50 |

On this specific CPU implementation, structured generation was about **27.4% lower in mean latency** and processed about **19.1% fewer tokens** than the old Frozen implementation.

That result does **not** mean autoregressive generation is inherently cheaper. At this commit, Frozen scoring still performed one full forward pass per candidate, duplicating prompt prefill. Batched candidate scoring was implemented only after this run.

## Engineering interpretation

The important outcome is not the 50% accuracy number.

This run establishes a reproducible same-base comparison and exposed a concrete systems bottleneck:

```text
Old Frozen path
Prompt + Candidate A -> Forward
Prompt + Candidate B -> Forward
Prompt + Candidate C -> Forward

Structured path
Prompt -> Generate bounded JSON
```

The next implementation has already changed Frozen scoring to:

```text
Prompt + [Candidate A, B, C]
          |
          v
single batched forward
```

and score caching now prevents raw/calibrated reports from re-running identical test inference.

A v4 run should therefore be treated as the first useful performance comparison of the optimized reference implementation.
